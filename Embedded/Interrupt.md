# Polling and Interrupt
Polling and interrupt are two ways for the CPU to handle peripheral events.

In polling, the CPU continuously checks a peripheral status register to see whether an event occurs. It is simple but consumes CPU time because the CPU is busy waiting.

In interrupt-based handling, the peripheral generates an interrupt signal when an event happens. The CPU can execute other tasks and only runs an ISR when service is required.

For example, UART reception can be implemented by polling RXNE (Receive Data Register Not Empty)
continuously, or by enabling UART RX interrupt and processing the received byte inside the ISR.

In embedded systems, interrupts are commonly used for time-critical or asynchronous events, while polling is suitable for simple periodic checks.

# Can you explain the difference between software interrupt and hardware interrupt?

Yes. In an MCU, interrupts can be generated from different sources, mainly hardware interrupts and software interrupts.

A hardware interrupt is triggered by a hardware event. The event can come from an external pin or from an internal peripheral module inside the MCU.

For example, an external GPIO pin can be configured as an interrupt source. When the signal changes, such as a rising edge or falling edge from a button press or sensor signal, the GPIO hardware detects this event and generates an interrupt request to the CPU.

Another example is an internal peripheral interrupt, such as UART receive interrupt. When UART receives a new byte, the UART peripheral sets an interrupt flag and sends an interrupt request to the NVIC. The CPU then jumps to the UART interrupt handler to process the received data.

The interrupt flow is usually:

1. A hardware event occurs, such as GPIO edge, UART reception, timer overflow, or ADC conversion complete.
2. The peripheral generates an interrupt request.
3. The NVIC receives the interrupt request and checks the priority.
4. The CPU saves the current context and jumps to the corresponding ISR.
5. After the ISR finishes, the CPU restores the previous context and continues execution.

On the other hand, a software interrupt is generated by software instead of a physical hardware event.

For example, on Cortex-M processors:

- SVC (Supervisor Call) is triggered by software and is commonly used for system calls.
- PendSV is a software-triggered exception commonly used by RTOS for context switching.

So, the main difference is the interrupt source:

Hardware interrupt → generated by hardware events, such as GPIO, UART, Timer, ADC, or external pins.
Software interrupt → generated by software instructions, such as SVC or PendSV.

In real embedded systems, hardware interrupts are mainly used to handle asynchronous events from peripherals, while software interrupts are usually used by the operating system or firmware framework for internal control purposes.
